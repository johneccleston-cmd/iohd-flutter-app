Stock Levels Audit

What the Stock Levels screen shows, where each number comes from, and where stock can be lost, duplicated or misreported. This is an audit only. Nothing was fixed, committed, deployed or written to the Sheet or the database.

Summary

Stock Levels is a read-only view of the Google Sheet. The screen itself is simple. Most of the risk sits in the write paths that change the Sheet: phone checkouts, barcode scans, cycle counts and the 8:31 AM staging flush.

Production is running the previous Stock Levels screen. The web build the backend serves was published on 16 Nov at 11:19. The rewrite of lib/inventory_screen.dart (sidebar filters, reorder-point statuses) landed in commit 4c646bf on 18 Nov and hasn't been published. The live screen applies a fixed "5 or fewer is low" rule and ignores reorder points, so today it shows 251 parts as Out of stock. 194 of those are parts the warehouse doesn't keep.

The five things that matter most

  1. About 30% of logged checkout lines never reduce stock. 142 of 470 job checkouts in PickedItems name a part with no Inventory row. Most are doors or service lines. Some are stocked parts under a different Service Fusion name: Stop Mold | 7' White has no row, while Weather Seal | Stop Mold | 7' White does. That part was missed 9 times (18 units), most recently today. The phone is told "success" anyway.
  2. Quantities of 1,000 or more get destroyed on the next checkout. Every write path reads the formatted cell with parseInt, which turns "1,250.00" into 1. Checking out one unit then writes 0. No part is over 1,000 today, but three Hardware parts have a reorder point of 3,000.
  3. Two requests at once lose a decrement, and a row edit mid-request overwrites the wrong part. Writes go to row numbers read a moment earlier, with no lock. Both cases reproduced against the real router code.
  4. Anyone holding the shared app key can add or remove stock. That key ships in the public web build. Barcode scan and checkout accept it with no signed-in person, and the "who" written to the log is whatever the caller sends.
  5. Different pages show different stock for the same part. The Inventory dashboard, Warehouse KPI page and Product Catalog read a Postgres copy last refreshed on 16 Nov. Stock Levels reads the live Sheet. Today 20 parts differ by 235 units in total. Example: Light Bulb for Operators is 163 on the Sheet and 0 on the dashboard.

Supporting signal: only 147 of 230 cycle-counted parts (64%) matched what the system expected, and the misses added up to 1,201 units.

Where the numbers come from

On-hand quantity lives in one cell per part: Inventory!D on the IOHD Inventory Sheet. No committed or reserved quantity exists anywhere, so "available" is the same number as "on hand".

On handSheet column D (formatted, e.g. "65.00")stockLevels.js sheetNumber strips commas and truncates to a whole number
Reorder atSheet column E; blank is treated as 0Same parser; 0 means the part isn't kept in stock
StatusDerivedRewrite: out = reorder point set and none on hand; low = at or below the reorder point; no reorder point and none on hand = Not kept in stock. Live build: a fixed threshold of 5.
Units on handDerivedSum of positive quantities in the app (4,366 today)
Part #, Location, CategorySheet columns A, C, G"N/A" part numbers are blanked; a blank category becomes "Uncategorized"

The second copy

Postgres table inventory_items holds its own qty and reorder_point. The Inventory dashboard, Warehouse KPI page and Product Catalog read it. Only the manual catalog import writes it; the old Sheet-to-Postgres migration (migrate_invnetory.js) is never called. It was last refreshed on 16 Nov at 15:52 UTC, and 30 rows haven't changed since 29 Sep.

Issue list

Ranked by severity. Each confirmed bug has evidence and a way to reproduce it. Reproductions marked "harness" ran the real backend router against an in-memory fake Sheet (repro_writes.js), with nothing sent to Google or Postgres.

C1 Checkouts under a different name never reduce stock CriticalConfirmed

Checkout matches the Service Fusion line name to Sheet column B exactly (lower-cased and trimmed). With no match, the PickedItems row is still written and the phone gets {"status":"success","itemsUpdated":1}, but no quantity changes.

  • 142 of 470 job checkout rows (30%) name a part with no Inventory row: 364 units across 67 names. Most are doors and service lines, which is expected.
  • Stocked parts missed under a short name. The matching Sheet row is my reading of the names: Stop Mold | 7' White (9 rows, 18 units, latest 18 Nov), Stop Mold | 16' White (10, 10), Punched Angle | 1-1/4" x 1-1/4" | 8' (11, 16), Punched Angle | 2" x 2" | 10' | Taxable (2, 6), Operator Parts | PUSHER SPRING KIT QUIET… (3, 7), Keypads | 877LM | LiftMaster (2, 3), Stop Mold | 7' Black (2, 4).
  • On the phone these show as "Not a stocked part", so nobody is prompted to fix the mapping.

Evidence: read-only snapshot of Inventory and PickedItems; inventory.js:343; harness case C4. Repro: check out Stop Mold | 7' White qty 2. The response is success and the Weather Seal row stays at 60.

C2 Quantities of 1,000+ are misread as 1 on every write path CriticalConfirmed (latent)

The Sheets API returns formatted values. stockLevels.js was fixed to handle "3,000.00", but the write paths still use parseInt, which stops at the comma.

PathLineCell "1,250.00" becomes
Checkout of 1inventory.js:3450 (should be 1,249)
Scan add 5inventory.js:3826 (should be 1,255)
Staging flushinventory.js:483Same as checkout

Apps Script undopicked_items_undo.gs:70-71Same misread

Today the highest quantity is 206, so nothing has crossed 1,000. Back Hang Nut, Back Hang Bolt and Small Driller have reorder points of 3,000, and the backend's own test fixture recorded Back Hang Nut at 1,250 on 16 Nov. Repro: harness cases C1a to C1d.

C3 Simultaneous writes to the same part lose one CriticalConfirmed

Each write reads the whole tab, computes a new value and writes it back, with no lock or version check. Two checkouts of the same part a few hundred milliseconds apart both start from the same number. The Apps Script undo also writes column D without coordinating with the backend.

Harness C2: Light Bulb at 163, checkouts of 2 and 3 at once. The log shows 5 taken; the Sheet ends at 160, not 158.

C4 A row inserted, deleted or sorted mid-request overwrites another part CriticalConfirmed

The write address is Inventory!D{index+1}, taken from a read made earlier in the same request. If anyone changes row order on the Sheet in between, the new quantity lands on a different part. Nothing on the Sheet is protected.

Harness C3: a row was inserted above while a Stop Mold checkout was in flight. Light Bulb was overwritten from 163 to 59, and Stop Mold stayed at 60.

C5 The shared app key alone can change stock CriticalConfirmed

requireAuth lets a request through with only the shared Bearer key, which ships in every app build and in the public web build. /scan_checkout (add or deduct any quantity) and /checkout_inventory do no further check. /cycle_count_update also accepts it while ENFORCE_USER_AUTH is off. The person recorded in the log is the caller-supplied techName.

Harness H-auth using the real auth.js: scan add of 500 with no user token returned HTTP 200. I didn't read production environment variables, so whether ENFORCE_USER_AUTH is on is unverified. The checkout and scan routes don't depend on it.

C6 The live screen misreports status for 247 parts CriticalConfirmed

The deployed build uses _kLowStockThreshold = 5 for every part. Rendered against today's Sheet it shows 251 Out and 64 Low.

  • 194 of the 251 "Out of stock" have no reorder point (not kept in stock).
  • 30 of the 64 "Low" aren't at or below their reorder point.
  • 23 parts that are at or below their reorder point show "In stock".

That's 247 parts in all. The Inventory dashboard uses reorder points, so the two pages disagree. The unreleased rewrite fixes this and shows 57 out, 57 low, 138 in stock and 194 not kept.

Evidence: the deployed main.dart.js rendered with the Sheet snapshot (screenshots below); code at git show 4c646bf^:lib/inventory_screen.dart, line 22.

C7 Dashboard, KPI and Catalog stock disagree with Stock Levels CriticalConfirmed

  • 20 parts differ in quantity (235 units in total) and 7 in status. Light Bulb for Operators is 163 on the Sheet and 0 in the database, so the dashboard counts it as low stock and the Warehouse KPI page as empty. Weather Seal Stop Mold 18' Dark Finish is 3 on the Sheet and 15 in the database.
  • The database has 857 active rows to the Sheet's 446, so the dashboard's "items" and valuation cover a different set of parts.
  • 12 Sheet parts have no database row by name, for example Shaft | Solid… with a double space, so the Catalog shows no stock for them.
  • No job keeps the two in step; refreshing depends on someone running the catalog import.

Evidence: read-only queries on inventory_items compared with the Sheet snapshot. Files: inventory_dashboard.js:43-60, employee_kpis.js (warehouse), catalog.js:342,522,667.

H1 Over-checkouts erase the shortfall, and undo then creates phantom stock HighConfirmed

Taking 5 when the Sheet says 2 writes 0 and records the 3-unit gap nowhere. Deleting that log row runs the Apps Script undo, which adds all 5 back, leaving 3 more than before.

Harness H-clamp; inventory.js:345; picked_items_undo.gs reverse_.

H2 Cycle count values go into the quantity cell unchecked HighConfirmed

countedQty is written as sent with USER_ENTERED. Negative numbers, decimals, text and formulas all land in column D, and a formula such as =10*10 is evaluated by Sheets. A non-string name or a null quantity crashes the request part-way through.

Harness H-cc-input; inventory.js:233-247.

H3 Cycle counts and their undo overwrite anything that happened since HighConfirmed (by code)

A count sets an absolute value, so checkouts between the shelf count and the submit are wiped. Deleting a CYCLE COUNT log row restores the "previous" value and wipes everything since. I didn't measure how often either happens.

H4 Warehouse staging is lost on any restart before 8:31 AM HighConfirmed mechanismOccurrence suspected

  • Early warehouse picks sit in a JavaScript Map until the 8:31 cron. A deploy or crash before then drops them: stock is never deducted, and the 8:30 audit can strike the warehouse.
  • Staging the same part for the same job twice replaces the first quantity instead of adding to it.
  • Whether a pick is staged depends on the client-sent x-user-role header or the typed techName.
  • 91 of 667 backend commits since 15 Sep landed on weekdays before 8:31 Chicago time, and each push auto-deploys.

inventory.js:15, 305, 321-328, 464-501.

H5 Retries can apply the same checkout or scan twice HighSuspected

Neither route accepts a request id. The phone's scan "Retry" resends after a failure, and a checkout that times out after 30 s may already have been applied. PickedItems has 18 exact duplicate pairs (same date, job, part, quantity and person). Some may be genuine second picks.

H6 A failure mid-checkout leaves a pick logged but not deducted HighConfirmed (by code)

The log append runs before the quantity read and write. If either fails, the log, the pick list and the 4 PM audit all treat the part as checked out while the Sheet still shows it on the shelf.

H7 Nobody can tell how fresh the numbers are HighConfirmed

The backend caches the Sheet for 60 s, and the screen stays alive in its tab and never refreshes itself. The live build shows "Updated 1:37 PM", which is when the app fetched, not when the Sheet was read. The rewrite removed even that. After a failed refresh, the rewrite says the list "may be out of date" but not from when.

H8 No way to correct stock from the office HighConfirmed

The screen is read-only: no part detail, no movement history, no adjust or receive action. Corrections mean editing the Google Sheet directly, which writes no PickedItems row and bypasses every check above.

H9 Duplicate part numbers send scans to the wrong part HighConfirmed

Six part numbers appear on two rows each, for example 4128527 on both the 893LM (row 211) and 893MAX (row 219) remotes. Scanning always takes the first row, so an 893MAX scan comes off the 893LM count.

Sheet snapshot; harness M-dup-part; inventory.js:377.

M1 Live search fails on multi-word queries MediumConfirmed

"stop mold 7' white" finds nothing because the live build matches the query as one unbroken substring, and the name has a " | " in the middle. The rewrite matches word by word and finds it.

M2 Typing in search stutters MediumMeasured

Typing 18 characters in the rewrite's search box produced 11 long tasks totalling 1.2 s, the worst 200 ms, with 446 parts (2.2 s and 256 ms with 5,000). The live build is similar, with a worst case of 308 ms. Every keystroke calls setState for the clear button (inventory_screen.dart:664), which re-filters, re-sorts and recounts the full list (_shown, _statusCount). Measured in headless Chrome on a 2017 Core i5; faster PCs will feel less.

M3 The rewrite is heavier than Product Catalog MediumRecommendation

  • Rows are about 50 px against the Catalog's 42 px. The grey header band plus grey striping adds weight; the Catalog uses a white header with small uppercase labels.
  • All 43 categories are always expanded, and the status caption permanently takes about 70 px of the sidebar.
  • Location is blank for 284 of 446 parts (64%), so most of that column shows "—".
  • Out-of-stock rows are red twice, in the quantity and the status. Long names wrap to two lines and make rows uneven.

M4 The live screen looks dated and wastes space MediumRecommendation

Four stat cards repeat the chip counts. The stock bar is quantity ÷ 20, which means nothing (anything at 20 or more is full). At 1280×600 only four rows fit above the fold. Loading is a lone brand-red spinner with no message during a Render cold start, which can take close to a minute.

M5 Fractional quantities are dropped or truncated MediumConfirmed

posInt turns 0.5 into 0, so the line is dropped entirely, and 2.5 into 2. The display parser truncates too. Low impact today because every Sheet quantity is a whole number, but job lines can carry fractional multipliers.

M6 Sheet data quality MediumPartly suspected

  • 58 names have leading or trailing spaces, and internal double spaces break name matching against the database.
  • 34 reorder points are blank; 9 costs are blank.
  • Back Hang Nut, Back Hang Bolt and Small Driller have reorder points of 3,000 but costs of $120 to $175. That looks like a reorder point in pieces against a cost per box, which would also skew valuation.

L1 Stock endpoint has no page permission check and leaks error text LowConfirmed

GET /get_full_inventory doesn't check stock.view, so anyone signed in, or holding the shared key, can read it. Cost isn't included. A 500 returns the raw Google error message.

L2 Stock goldens are stale and the golden test only runs on Windows LowConfirmed

inventory_render_test.dart reads C:/Windows/Fonts with no existence check, so it errors elsewhere. Its inv_stock_* images show the pre-18 Nov design, so on Windows those cases would fail against today's source.

L3 Live build ignores 401 and reads a field the API never sends LowConfirmed

An expired session shows "Couldn't load inventory (status 401)" instead of signing out. It also reads sku, which the backend doesn't send, so part numbers never appear. Both are fixed in the rewrite.

L4 Error state repeats itself; mixed date formats in the log LowConfirmed

The rewrite's error state reads "Could not load stock levels" followed by "Could not load stock levels (server error 500)". PickedItems mixes 11/18/2026 and 11/18/26 (80 rows) because the date comes from the client.

Can imports overwrite manual changes?The catalog import overwrites database quantities with its export's Sheet values. On the Sheet, a cycle count overwrites checkouts made since the shelf count, and deleting a count's log row overwrites everything since.
Duplicate rows possible?Yes. Nothing enforces unique names or part numbers. No duplicate names today; six duplicate part numbers.

Can syncs run at once?Yes. Requests, the 8:31 cron and the Apps Script trigger all write column D with no shared lock (C3).

Redesign direction

Start from the rewrite, which already has the right structure, and bring it to Product Catalog density without copying the Catalog's editing tools.

Header and toolbar

  • Ribbon shows when the Sheet was read ("Sheet read 1:37 PM") and warns past a few minutes
  • One toolbar line: search (with / to focus), Needs attention, count on the right
  • No stat cards; status counts live in the filter list

Table

  • 42 px rows, white, hairline dividers; uppercase header like the Catalog
  • Part name with part number beneath in muted mono; Location shown only when set
  • One status signal per row: a pill; quantity bold only when it needs action
  • Tabular figures; "Reorder at" muted when 0

Filters

  • Collapsible groups and a collapsible sidebar, matching the Catalog
  • Status caption moves to a tooltip on the group title
  • Categories collapsed past the top 8, with a filter box

New, and where the value is

  • Part drawer: movement history, last count, linked catalog product, Sheet vs database mismatch
  • "Unmatched checkouts" view listing names that reduced nothing (C1)
  • Adjust, receive and count actions with reason codes, behind a stock.adjust permission

Implementation phases

  1. Stop silent stock loss (backend only)

    • Use one quantity parser everywhere: write paths, warehouse value and the Apps Script
    • Validate cycle-count input and write values as RAW numbers
    • Require a signed-in person for every stock write, and take identity from the token
    • Add request ids for checkout and scan; log only after the quantity write succeeds
    • Serialize writes per part (one instance makes an in-process lock enough for now), re-read the row by part key just before writing, and refuse when it moved
    • Persist staging in Postgres; add the write-path tests

  2. One source of truth and real part links

    • Decide the system of record. Recommended: Postgres with an append-only stock movement ledger, the Sheet becoming a published view
    • Short of that, a scheduled Sheet-to-database mirror
    • Match checkouts by catalog product id (inventory_item_id exists) instead of name; report unmatched lines
    • Clean up duplicate part numbers, spacing and units

  3. Ship and refine the Stock Levels screen

    • Freshness stamp, Catalog-density table, collapsible filters, the search rebuild fix
    • Part drawer and unmatched-checkouts view
    • Fit tests at all four sizes; golden refresh only with your OK

  4. Office adjustments

    • Adjust, receive and count dialogs with confirmation, reason, permission and ledger entry, replacing direct Sheet edits

  5. Release

    • Publish the web build and push the backend, each with your OK, then verify on production reads
